## Diagnosis

The failing signature — a borderline answer saturating to 5.0 and tying
strong — is the exact failure mode the v0.1 judge redesign fixed (see
`evals/reports/2026-07-26-v01-gate.md`), re-emerging intermittently on one
triplet. Two lines of evidence say this is judge-side nondeterminism, not a
v0.2 code regression:

1. **Control probe (run 4):** the untouched v0.1.0 code, re-run in the same
   window with the same key, passed while the v0.2 tree was failing — and
   then the v0.2 tree itself passed (run 5) with no code change in between.
2. **Code-path analysis:** the only v0.2 change inside the judged path is
   the transient-error backoff wrapper, which issues call-for-call identical
   requests on success (same prompt, same seeds, same config); the
   interviewer-instruction changes are not imported by the eval path at all.
   The scoring model is `gemini-2.5-flash`, and the provider exposes no
   dated snapshot to pin (verified against the models list on 2026-08-01),
   so provider-side drift can be neither selected around nor ruled out.

Commits after run 5 and before the v0.2.0 tag touch only interviewer
instruction text, web session-room/report rendering, and docs — none inside
the judged path — so run 5 stands as the gate result for the tagged tree.

**Consequence:** with N=3 triplets, one boundary case decides the gate.
Growing the golden set (E1) moves up the roadmap, and recording per-variant
scores for *passing* trials (so flicker margins are visible in the artifact,
not just failures) is queued with it.
